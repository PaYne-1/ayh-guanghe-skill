# 11 节点执行流程

## 0. 启动渠道选择与锁定

- 在扫描产品素材、创建批次、查询价格、生图、dry-run 或付费调用之前，必须选择 `GPT 网页端` 或 `第三方 API`。
- 选择 `第三方 API` 时，确认并封存 `api_name`、`base_url`、`model`、`api_key_env`、`unit_price_yuan`、`batch_budget_yuan`；只保存环境变量名，不保存密钥值，图片 API 批次预算独立记账。
- `approve-start` 将选择写入批准清单后，渠道在批次内锁定，禁止自动切换；故障只能按同一渠道的失败/重试流程处理。切换渠道必须新建批次。

## 1. 产品素材

- 用户给出任意产品文件夹路径；产品名默认取最后一级目录名，可覆盖。
- 只读取第一层 PNG/JPG/JPEG/WEBP，不递归，不修改原图。
- 用户提供卖点后直接使用，不二次确认。每个产品单独维护卖点库，不保存脚本分镜库。

## 2. 内容策划

一个卖点对应一条独立视频。分析适用人群、使用场景、核心痛点、切入角度和选题方向，不判断疾病或伤情。输出内容契约规定的完整 JSON。

标题、正文和话题标签先分别保存为 `_工作文件/生成过程/标题.txt`、`_工作文件/生成过程/发布正文.txt` 与 `_工作文件/生成过程/话题标签.txt` 候选。内容契约通过后由运行器使用启动自动授权，按各自 SHA-256 晋升；无需再逐项征求同意。

默认每个卖点一套。用户指定总数量时平均分配，余数从第一个卖点开始分配。例如 5 个卖点生成 23 条：5、5、5、4、4。

## 3. 分镜图和封面图

- 分镜首帧、合理尾帧和完整封面都必须按 [生图渠道路由](image-generation-routing.md) 执行，使用启动时已选择并锁定的渠道。
- 脚本按启动确认单顺序选取前 3 张有效产品图：第一张为主参考，其余最多 2 张为辅助参考；不额外调用模型选择。
- 每条由已锁定渠道生成 1 张竖屏分镜原图到 `_工作文件/生成过程`。不进行人工图片审核，也不进行模型视觉审核；文件可解码、画幅、尺寸归一化和 SHA-256 等本地免费技术检查通过后，`accept-image` 自动晋升为一级 `分镜图.png`。
- 正式分镜落盘后，由同一已锁定渠道固定生成 1 张合理尾帧原图到 `_工作文件/生成过程/尾帧候选.png`，提示词要求主体继续前进约 1–1.5 米。尾帧不得复用首帧；通过本地免费技术检查且 SHA-256 与首帧不同后，`accept-image` 自动晋升为一级 `尾帧图.png`。一级 `分镜图.png` 作为 `first_frame`，一级 `尾帧图.png` 作为 `last_frame`。
- 技术失败的重试次数由 `pipeline_policy.json` 和运行器计数限制；耗尽后仅标记该视频需要人工处理，批次其他项目继续。
- 从用户确认的封面参考文件夹第一层选风格图，以合格分镜和产品图为参考，由同一已锁定渠道一次生成画面、版式及准确标题组成的完整电商封面；不得重画或改变产品结构、人物和构图主体。
- 封面风格图按文件名排序，脚本用本批次视频序号对参考图数量取余进行轮换。此选择可重复恢复，不消耗模型调用；当前不维护跨批次风格轮换状态。
- 封面提示词要求标题与 `_工作文件/生成过程/封面标题.txt` 一致，并一次生成完整画面。禁止生成底图后代码叠字；下载结果不进行文字、构图或产品结构二次审核。
- 两种模式都在文件可解码、9:16、尺寸与哈希技术检查通过后，使用本批次自动执行授权晋升为一级 `封面图.png` 并进入下一步。

## 4. 发布正文与话题标签

根据最终脚本和合格分镜生成 80–150 个汉字，标签不计入字数。人物、性别、场景、卖点与脚本一致。爱优护配置追加固定四个标签。

正文候选保存在 `_工作文件/生成过程/发布正文.txt`，标签候选保存在 `_工作文件/生成过程/话题标签.txt`。两者是独立产出，内容校验通过后由运行器绑定启动授权与各自 SHA-256，并分别晋升。

## 5. 视频参数

MiniMax-H3、15 秒、9:16、默认 768P；2K 只能在启动确认时选择。所有项目固定使用 `minimax_h3_lightx2v` 首尾帧工作流，关闭 AIGC 画面水印。每条脚本必须恰好包含老人和一名陪护者或家属两个不同的 `speaker_id`，两人全程在画面中自然对话；缺少任一角色、存在画外音或同一角色包办全部台词时不得进入视频节点。

`script_segments[].speaker_id` 是唯一说话人分配依据。首尾帧工作流没有独立参考音频输入时，允许 MiniMax-H3 生成原生双角色对话；`prompt` 必须逐句标注说话人，指定陪护者提问、老人回答唯一卖点，并由脚本指定角色说出下单类行动指令。成片必须逐句核验台词、顺序、角色归属、声音可理解度和结尾行动指令；自问自答、串角色、漏句、听不懂或缺少行动指令均判为不合格。

固定使用合理尾帧首尾帧模式：以通过免费技术检查并自动晋升的竖屏 4K 一级 `分镜图.png` 作为 `2160×3840` 的 `first_frame`，以独立生成、通过相同技术检查且哈希不同的一级 `尾帧图.png` 作为 `last_frame`。两张一级图必须各自绑定自动授权的有效 `passed` 事件且 SHA-256 不同，才可进入付费确认。

已通过本地技术检查的分镜是视频提示词的视觉基准。视频应保持人物完整度、产品角度、构图、亮度、曝光、白平衡和色温，只增加已策划的轻微动作与对白。人物被裁切、产品朝向改变、镜头重新取景或明显明暗色调漂移由用户在最终视频验收中判断；本地技术指标不替代视觉一致性验收，也不额外触发模型逐段审核。

首尾帧视频允许真实直线行驶产生连续、自然的视角演进和轻微亮度波动，这些变化记录时间点进入复核，不单独自动判为硬失败；切镜、突然切近景、人物持续裁切、产品结构变形、轮椅未真实行驶或首尾脱离已通过分镜仍是不合格。

视频全程必须一镜到底，禁止切镜、跳切、转场、突然推近、突然拉远和景别突变。允许摄影机缓慢、连续、平稳运镜；人物完整度、轮椅角度、主体构图、曝光、白平衡、亮度和色温写入视频创作要求，实际是否合格统一由用户在最终视频验收中判断。

付费提交前必须确认全部口播能在 15 秒内按自然聊天语速完整说完并留出结尾停顿。超限时先自动精简台词，保留本条唯一卖点、使用改善和结尾了解引导，重新检查通过后才可提交。禁止用加速抢读、漏词、改词或截断尾句来迁就时长。

以上“一镜到底、连续平稳运镜、完整双人对话口播”三项硬规则必须覆盖整个0–15秒，包括首帧、全部中间过程和尾帧；不得只在开头或结尾满足。已通过分镜首帧和独立生成的合理行驶尾帧只加强端点约束，视频提示词仍必须逐项声明三项规则全程有效。

## 6. 提交 AutoDL.Art

先内容、图片、预算和请求哈希检查，再 dry-run。运行器顺序执行，生成 `提交请求.json`，包含逐句说话人台词与两张已晋升图片的 data URI。正式提交检查项目清单、单价、总预算、分辨率、实际 payload 与首尾帧哈希，并在跨进程锁内先保留费用和请求身份再 POST；存在 task_id 时只恢复原任务。

## 7. 保存 task_id

成功响应后立即写入本条 `_工作文件/任务状态/任务信息.json` 和批次 `批次任务表.json`。已有 task_id 或相同请求哈希不得重复提交；超时且不确定是否提交成功时标记 `SUBMIT_UNKNOWN`。

## 8. 查询状态

默认每 20 秒查询，网络错误最多连续重试 5 次，连续等待 60 分钟后标记查询超时但保留 task_id。批量结束统一汇报，不逐条打扰用户。

## 9. 下载 MP4

成功后立即下载为 `_工作文件/生成过程/视频候选.mp4.part`，完成并校验后原子改名为 `_工作文件/生成过程/视频候选.mp4`。下载最多 4 次。检查非空、容器、约 15 秒、9:16、目标分辨率、有效非静音音轨和可解码画面。候选不得直接命名为一级 `视频.mp4`。

## 10. 批量人工验收

运行器生成 `批次验收报告.html`，仅为已有真实提交身份、候选文件和匹配哈希/版本技术证据的视频生成卡片；未提交或等待本地修复的项目不参与本次验收。报告显示候选相对路径和 SHA-256，不把候选当成一级正式产出。用户为报告中的每条视频选择通过或不通过；不通过必须写原因。最终视频永远由用户验收。已通过的兄弟项目可以先晋升；另一个项目完成 V02 后，再次报告可使用该兄弟项目的已晋升路径，仍须匹配原技术检查哈希和版本。

旧格式批次结果没有候选路径和 SHA-256 时只保存反馈，不能自动晋升。视频必须通过 `review-output` 绑定本次候选哈希和用户明确通过反馈后，才晋升；最终文件按 [交互与最终交付契约](delivery-contract.md) 使用清洗后的发布标题命名，并在当前对话内展示。

用户通过后不能停在“候选已合格”：立即执行 `review-output`、确认标题化 `.mp4` 已进入单条任务一级目录、运行 `audit-outputs`，完成全片解码检查并把任务状态更新为 `COMPLETED`。任一交付检查失败时继续修复，不得先宣称完成。

运行器返回 `DONE` 前重新执行整批七项产出审计，包括先前已完成、未参加本次验收的兄弟项目。缺失、哈希损坏或已撤下的产出返回 `LOCAL_OUTPUT_REPAIR_REQUIRED`，指出视频 ID、具体产出和 `audit_path`；完整历次证据保存在批次 `_交付审计/`，最新汇总为 `批次交付审计.json`。从原有效通过事件绑定的快照恢复准确字节；撤销的通过记录需要重新取得明确通过，不能擅自复活。恢复后调用 `run-local --batch "批次目录"`，此修复分支只重新审计，不准备 payload、不提交、轮询或下载，不消耗 V02。全部项目再次通过整批审计后才结束。

## 11. 复盘与一次重跑

失败原因分流到内容、分镜、封面、音频、视频、API、轮询、下载或模型能力边界。V01 视频验收不通过时，先向用户反馈失败原因、异常时间点和候选路径；只有用户单独授权该视频费用后才调用 `approve-rerun` 并允许进入 V02 一次。V02 仍失败则反馈后停止，不得生成 V03。正式规则在批次启动时加载一次，由脚本生成紧凑的生效规则输入；运行时不在每个节点反复把完整规则文档送入模型上下文。

缺少密钥、提交前校验、轮询网络、下载或本地解码失败按项目保存为可恢复问题。`next` 返回 `LOCAL_WORK_REQUIRED` 和原因；修复环境后调用 `run-local --batch "批次目录"`，继续原 V01/V02 或已知 task_id，不重新付费、不要求新的 V01 授权。尚未 POST 的项目没有 V02 资格，不能用重跑解决环境问题。提交是否成功不确定且没有 task_id 的项目仍需核对原任务，不能自动重复 POST。

人工重跑队列保存在 `human_gate`，模型诊断动作单独保存在 `pending_action`。诊断前保留动作、接收后继续 `next`，不会丢掉尚未批准的其他视频；逐条批准只移除该条队列项。

## 文件结构

```text
产品文件夹/生成视频/YYYYMMDD_批次NNN/
├─ V001_卖点_封面标题/
│  ├─ 标题.txt
│  ├─ 发布正文.txt
│  ├─ 话题标签.txt
│  ├─ 分镜图.png
│  ├─ 尾帧图.png
│  ├─ 封面图.png
│  ├─ 清洗后的发布标题.mp4
│  └─ _工作文件/
│     ├─ 任务状态/任务信息.json、查询结果、提交请求与 AutoDL 响应
│     ├─ 生成过程/标题.txt、发布正文.txt、话题标签.txt、分镜候选、尾帧候选、封面候选、视频候选、提示词与转写
│     ├─ 验收记录/产出验收记录.json、口播音轨验收.md、自动验收报告.md、人工验收结果.md
│     └─ 历史版本/验收候选、候选版本、未通过或待验收、已撤换产出、视频版本及失败版本
├─ 批次任务表.json
├─ 批次汇总.md
├─ 批次验收报告.html
├─ 批次验收结果.json
└─ 批次验收结果.md
```

单条任务第一级只允许七项经过明确通过的最终产出和 `_工作文件`。每个一级文件必须能在 `产出验收记录.json` 中找到同一产出名、同一 SHA-256 且最新决定为 `passed` 的事件。没有明确通过则一级目录不保留对应文件；失败、撤销、无记录、记录损坏或哈希不一致的文件由 `audit-outputs` 移入 `历史版本/未通过或待验收`。过程文件必须分别写入 `_工作文件/任务状态`、`_工作文件/生成过程`、`_工作文件/验收记录`、`_工作文件/历史版本`。

验收事件按追加顺序判定最新决定，不依赖系统时间排序；写入时使用跨进程锁。`review-output` 将被验收字节复制为 `_工作文件/历史版本/验收候选` 下的不可变快照，事件绑定该快照。重复生成同名候选前，旧候选移入 `历史版本/候选版本`。晋升采用同盘临时文件、哈希校验和失败回滚，不能因复制失败丢失原一级产出。

```powershell
python scripts/pipeline_runner.py accept-image --batch "批次目录" --video-id "V001" --artifact "分镜图.png" --source "下载原图路径" --action-id "next返回的动作ID"
python scripts/pipeline_runner.py accept-image --batch "批次目录" --video-id "V001" --artifact "尾帧图.png" --source "下载原图路径" --action-id "next返回的动作ID"
python scripts/workflow_cli.py audit-outputs --item-dir "单条任务目录"
```

后续节点读取一级产出前必须再次校验验收事件和哈希，不能只判断文件是否存在。旧 Markdown 或旧批次 JSON 只供查阅，不得推断或补造 `passed` 事件。
