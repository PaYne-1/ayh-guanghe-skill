# 学习模式自动复盘与规避设计

## 目标

学习模式执行期间，用户提出的每个问题都必须自动形成可追溯复盘。解决方案在本次任务重跑中验证有效后，系统无需再次询问即可升级为正式规则；后续任务启动时必须自动加载匹配规则，并在相关节点执行前应用，从而规避已经验证的问题。

## 范围

本设计覆盖：用户反馈采集、问题归类、自动复盘、候选经验、重跑验证、正式规则升级、规则检索、执行前注入、冲突处理、命中记录和审计。

本设计不改变以下边界：

- 最终视频仍由用户人工验收；
- 每条视频仍只允许 V02 一次付费重跑；
- 未验证方案不能成为正式规则；
- API、余额、预算和模型能力边界仍按现有暂停规则处理；
- 不保存标题库、脚本库或分镜库，只保存可复用的问题解决规则与产品卖点。

## 三层知识结构

知识目录分为三层：

```text
知识目录/
├─ 产品卖点库/
├─ 候选经验/
└─ 正式规则/
```

### 候选经验

用户在学习模式中提出问题后立即生成，记录原始反馈和系统复盘，但不参与后续任务自动执行。

### 正式规则

候选解决方案在本次 V02 重跑中验证有效后自动生成。正式规则是后续学习模式和自动模式唯一可以自动加载并执行的经验来源。

### 历史与状态

规则不物理删除。被替代、冲突或验证失效的规则改为 `superseded` 或 `disabled`，保留完整审计记录。

## 用户问题捕获

学习模式中，用户针对当前任务提出的纠正、质疑、不通过原因或修改要求都视为问题反馈。系统必须保留用户原话，并绑定：

- 产品 ID、产品名称和产品路径；
- 批次 ID、视频 ID 和候选版本；
- 发生节点；
- 使用的模型、工作流和生成渠道；
- 相关候选文件路径与 SHA-256；
- 自动验收证据和用户验收决定；
- 记录时间。

闲聊、与任务无关的问题和没有可执行纠正含义的消息不得写入候选经验。

## 自动复盘结构

每条问题必须生成一个结构化复盘，至少包含：

```json
{
  "issue_id": "稳定唯一标识",
  "status": "candidate",
  "scope": {
    "product_id": "产品标识或 null",
    "node": "content|storyboard|cover|audio|video|api|polling|download|review",
    "model": "模型或 null",
    "channel": "生成渠道或 null"
  },
  "user_feedback": "用户原话",
  "symptom": "可观察失败表现",
  "root_cause": "基于证据的根因；证据不足时明确写未知",
  "solution": "本次重跑要执行的最小修改",
  "prevention_rule": "下次任务执行前可直接检查或执行的规则",
  "validation": {
    "method": "如何判断方案有效",
    "expected": "预期结果",
    "result": "pending"
  },
  "evidence": [],
  "source_batch": "批次路径",
  "source_video_id": "视频 ID",
  "created_at": "ISO-8601 时间"
}
```

根因证据不足时不得编造原因。此时可以提出保守解决方案，但 `root_cause` 必须标记为未知或待验证。

## 问题归类

系统根据最早需要返回修改的节点归类：

| 问题类型 | 返回节点 | 典型内容 |
|---|---|---|
| 内容 | content | 卖点、痛点、人物、标题、脚本错误 |
| 分镜 | storyboard | 产品结构、Logo、人物、构图、场景错误 |
| 封面 | cover | 版式、底图、标题呈现错误 |
| 音频 | audio | 漏词、截断、音色、说话人、顺序错误 |
| 视频 | video | 动作、口型、切镜、构图漂移、对白错误 |
| API | api | 参数、鉴权、请求格式或提交失败 |
| 轮询 | polling | 查询方法、超时、状态恢复错误 |
| 下载 | download | 文件损坏、地址失效、原子落盘错误 |
| 模型边界 | review | 多次验证仍无法稳定完成的能力限制 |

一个反馈涉及多个节点时可以产生多条候选经验，但每条只能描述一个可独立验证的问题。

## 验证与自动升级

1. 首次问题产生候选经验，验证状态为 `pending`。
2. 系统把候选中的 `solution` 应用到本条唯一一次 V02 重跑。
3. 用户明确通过 V02，且与该问题对应的自动检查通过时，候选验证结果改为 `passed`。
4. 学习模式下，验证通过后自动升级为正式规则，不再单独询问用户是否升级。
5. V02 仍不通过时，验证结果改为 `failed`；失败方案不得进入正式规则。
6. 无法判断 V02 是否解决该问题时，验证结果保持 `inconclusive`，不得升级。
7. 模型在合理表达和唯一一次重跑后仍无法稳定完成时，记录模型能力边界；能力边界可以作为正式规避规则，但必须明确限定模型和适用场景，并以“不再自动付费重试或改用稳定表达”为预防动作。

“视频整体通过”不能自动证明所有候选方案有效。每条候选必须有与其验证方法对应的检查结果。

## 正式规则结构

正式规则至少包含：

```json
{
  "rule_id": "稳定唯一标识",
  "version": 1,
  "status": "active",
  "scope": {
    "product_id": "产品标识或 null",
    "node": "节点",
    "model": "模型或 null",
    "channel": "渠道或 null"
  },
  "trigger": "可观察的适用条件",
  "required_action": "执行前必须采取的动作",
  "validation_check": "执行后必须检查的结果",
  "source_issue_id": "候选问题 ID",
  "source_batch": "来源批次",
  "source_video_id": "来源视频",
  "verified_candidate_sha256": "通过候选哈希",
  "verified_at": "ISO-8601 时间",
  "hit_count": 0,
  "last_hit_at": null
}
```

正式规则必须写成可执行条件和动作，不能只保存“注意质量”“避免出错”等空泛总结。

## 下次任务自动加载

每次初始化学习模式或自动模式时，必须读取 `正式规则/` 中所有 `active` 规则，并按以下条件筛选：

1. 当前产品 ID 匹配的产品专属规则；
2. 当前节点匹配的规则；
3. 当前模型或渠道匹配的规则；
4. 没有产品限制的全局规则。

任务启动确认单必须记录：

- 正式规则库路径和版本摘要；
- 本次命中的规则 ID；
- 每条规则适用的节点；
- 本次未加载规则及排除原因。

进入相关节点前，系统必须把命中的 `required_action` 注入该节点的检查单、提示词约束或确定性校验。只在启动确认单中列出规则但执行时不应用，视为未实现自动规避。

## 冲突与优先级

规则冲突时按以下顺序决定：

1. 产品专属规则高于全局规则；
2. 节点、模型和渠道限定更精确的规则优先；
3. 同等范围内，较新且验证通过的版本优先；
4. 新规则替代旧规则时，旧规则标记为 `superseded` 并记录替代者；
5. 无法自动消解的冲突必须在启动确认时报告，不得静默选择。

## 命中记录与持续复盘

正式规则每次被加载并实际应用后，追加命中事件并更新 `hit_count` 与 `last_hit_at`。如果应用规则后同类问题仍再次发生：

- 保留旧规则及本次命中证据；
- 创建新的候选经验，说明旧规则为何不足；
- 新方案验证成功后生成新版本并替代旧规则；
- 不得篡改旧规则的历史验证结果。

## 失败与恢复

- 知识库文件损坏：暂停当前批次的创作提交，保留原文件并报告，不得静默清空规则库。
- 写入中断：使用临时文件、原子替换和跨进程锁，避免部分 JSON。
- 重复反馈：按产品、节点、症状和来源候选哈希去重；重复内容追加证据，不重复创建相同规则。
- 未知提交状态：不把技术不确定性总结为创作规则。
- 自动复盘失败：保留用户原话和证据，标记待人工归类；不得因此丢失反馈。

## 验收标准

实现完成后必须满足：

1. 学习模式中的任务相关用户问题自动生成候选经验；
2. 候选包含原话、症状、根因、方案、预防规则和验证方法；
3. V02 对应验证通过后自动生成正式规则；
4. 验证失败或不确定的方案不会进入正式规则；
5. 新批次初始化时能自动列出匹配的正式规则；
6. 相关节点执行前能读取并应用规则动作；
7. 规则冲突、替代、命中和再次失败均可追溯；
8. 现有人工最终验收、预算和最大重跑次数约束不被绕过。
