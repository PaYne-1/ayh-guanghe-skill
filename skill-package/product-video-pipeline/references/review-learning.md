# 批量验收与经验学习

## 自动验收材料

每条视频生成：

```text
_工作文件/生成过程/视频候选.mp4
_工作文件/验收记录/自动验收报告.md
_工作文件/验收记录/视频技术检查.json
```

默认自动检查只做本地容器、时长、分辨率、音轨和全片解码，保存绑定候选 SHA-256 的技术证据。产品、人物、镜头、对白和观感在最终视频人工验收时判断。若用户另行请求内容分析，其模型调用必须先保留诊断次数；不得每段视频自动重新开长对话。自动验收只形成证据，不替用户做最终决定，也不授权重新生成。

自动验收是必要前置证据，但不能代替用户明确通过，也不能触发最终晋升。只有 `review-output` 针对具体候选文件写入用户确认、候选相对路径和 SHA-256 后，`passed` 文件才能成为一级按发布标题命名的 `.mp4`；验收事件中的逻辑产物名保持 `视频.mp4`。没有明确通过时一级目录不保留视频。

每条视频的验收证据必须同时绑定一级 `分镜图.png`（`first_frame`）和一级 `尾帧图.png`（`last_frame`）各自的自动授权 `passed` 事件与 SHA-256，以及本地免费技术检查结果；两个哈希必须不同。图片不进行人工或模型视觉审核。缺少任一项时不得进入视频付费提交或最终验收。

单镜头连续性、运镜稳定性和口播完整性由用户在最终视频验收时检查全片，发现切镜、跳切、转场、突然改变景别、人物出框、构图明显漂移、口播漏句或尾句被截断时记录原因和异常时间点。默认不调用模型做逐段视觉检查或语音转写，不把本地解码通过当作这些创作要求已通过。

脚本阶段本地校验 `script_segments[].speaker_id` 对应两位人物并逐句写入视频提示词。成片音色身份、角色串词、顺序错误或老人自问自答统一由用户在最终批量视频验收时判断，不新增系统逐段模型审核或独立试听确认节点。

所有首尾帧视频中，真实直线行驶产生的自然视角变化、轻微亮度波动或连续插值过渡必须在报告中记录时间点并进入复核，不得单独自动判为硬失败。切镜、人物裁切、产品结构变形、轮椅未真实行驶、角色自问自答、台词串角色、语音不可理解或缺少下单类行动指令仍为硬失败。用户明确验收结论为最终状态；自动报告和异常时间点继续保留自动检查证据，不得删除或改写为未发生。

用户明确通过优先于自动验收结论。若同一候选此前已有自动或人工 `failed`，不得改写、删除或伪装该历史；应对完全相同的候选字节追加新的 `passed` 事件，以最新事件作为交付决定，然后晋升并审计。用户说“最终合格视频”“这个版本通过”或同义明确表述时，视为对已指明候选的通过决定，不再反问是否通过。

## 批量验收

```powershell
python scripts/pipeline_runner.py next --batch "产品文件夹/生成视频/批次目录"
```

在运行器返回 `USER_FINAL_REVIEW_REQUIRED` 时打开其 `report_path`。报告只包含真实候选，显示相对路径和 SHA-256；这只是预览证据，不代表已经晋升。尚未提交或待修复项目不需要填验收决定。每条卡片选择“通过”或“不通过”；不通过必须写原因，可以写修改建议。点击“完成验收”下载 `批次验收结果.json`，再回写：

```powershell
python scripts/pipeline_runner.py complete-review `
  --batch "批次目录" `
  --result "下载的批次验收结果.json"
```

脚本生成批次 JSON/Markdown、每条 `_工作文件/验收记录/人工验收结果.md`，并把失败项写入候选经验。所有自动或人工验收证据都进入 `_工作文件/验收记录`，不占用单条任务第一级。

旧格式批次结果不包含候选路径和 SHA-256 时不能自动转换为 `passed`。用户明确通过后执行 `workflow_cli.py review-output`；任务结束或整理时执行 `workflow_cli.py audit-outputs`，撤下无证据、失败、撤销或哈希不一致的一级文件。

## 一次重跑

问题按以下节点分流：

| 问题 | 返回节点 |
|---|---|
| 痛点、脚本、人物、标题错误 | 内容策划 |
| 产品外观、Logo、人物图或首尾结构错误 | 正式分镜或合理尾帧 |
| 正文错误 | 发布正文 |
| 标签错误 | 话题标签 |
| 动作、对白、嘴型、视频提示词错误 | 视频提示词与提交 |
| API、轮询或下载错误 | 技术恢复，不改创作内容 |
| 模型无法稳定完成 | 改用更稳定表达，并记录模型能力边界 |

每条只保留 `V01_初次生成` 和 `V02_唯一一次重跑`。V02 仍不通过，标记人工专项处理，不发起第三次付费任务。

V01 或 V02 自动验收不通过后，必须先把候选路径、失败原因和异常时间点反馈给用户，并明确询问是否重跑。只有用户明确同意重跑后才能发起下一次生成；自动生产模式、启动时的批次授权或“全程不需要确认”都不包含失败重跑授权。用户未回复或不同意时保留现有候选与证据并停止，不得自动提交付费任务。V02 已是唯一一次重跑，失败后只反馈，不得生成 V03。

失败反馈与重跑是两个独立动作：先展示现有候选和审核依据，再等待用户选择。不得把自动审核的 `failed` 当成付费重跑指令，也不得因为已经预留重跑预算就直接消费。

## 学习规则

- 学习模式中的任务相关用户反馈和首次失败自动形成结构化候选经验。
- 候选方案应用到 V02 后，只有对应自动检查通过且用户明确通过该候选，才自动升级正式规则；无需再次询问是否升级。
- 重跑仍失败时记录为 MiniMax-H3 或对应模型能力边界，不把失败方案升级。
- 自动模式只读取正式规则；新候选不能自动污染正式库。
- 卖点库按产品独立保存；不保存标题库、脚本库或分镜库。
- 后续任务启动时加载一次匹配的正式规则，由脚本生成紧凑的生效规则输入并执行 `required_action`；运行时不在每个节点反复读入完整规则文档。
